# 서비스 소개 온보딩 이탈 분석

## 목적과 범위

처음 사용하는 사람이 알람의 동작 방식, 목적지와 반복 간격의 의미, 알람을 끈 뒤 할 일을 이해할 수 있도록 네 페이지로 소개한다. 온보딩을 시작한 사용자가 어느 페이지에서 진행을 멈추는지 측정한다. Android와 iOS 모두 서비스 소개 → 목적지 안내 → 반복 간격 안내 → 출발 안내의 4단계다.

온보딩에서는 알람을 생성·예약하거나 위치·알림 권한을 요청하지 않는다. 마지막 `시작하기` 요청이 수락되고 온보딩 완료 상태가 로컬에 저장되면 완료로 판단한다. 첫 알람 생성은 홈 진입 이후의 별도 행동이다.

## 이벤트 계약 v2

| 이벤트 | 발생 시점 | 파라미터 |
| --- | --- | --- |
| `tutorial_begin` | 첫 소개 페이지가 최초 표시될 때. 앱 재실행 후 중복 기록하지 않는다. | `flow_name`, `flow_version`, `step_count` |
| `onboarding_step_viewed` | 실제 페이지 표시. 스와이프·다음 버튼·이전 페이지 이동으로 다시 표시되는 경우도 포함한다. | 공통 파라미터 + `step_name`, `step_index` |
| `onboarding_submit` | 마지막 페이지의 `시작하기` 요청이 수락된 직후, 완료 상태를 저장하기 전에 기록한다. 저장 실패 후 수락된 재시도도 포함한다. | 공통 파라미터 + 마지막 페이지의 `step_name`, `step_index` |
| `tutorial_complete` | 온보딩 완료 상태의 로컬 저장까지 성공한 때. 알람 저장·예약이나 권한 허용에 의존하지 않는다. | `flow_name`, `flow_version`, `step_count` |

- `flow_name`: 문자열 `service_introduction`.
- `flow_version`: 정수 `2`.
- `step_count`: 두 플랫폼 모두 정수 `4`. 기존 파라미터 이름을 유지하며 페이지 수를 뜻한다.
- `step_name`: `introduction`, `destination`, `interval`, `departure`.
- `step_index`: 해당 페이지의 1부터 시작하는 순서. 두 플랫폼 모두 submit은 `departure`/`4`다.
- OS 구분은 Analytics의 기본 플랫폼 정보를 사용한다.

옆 페이지의 사전 구성이나 스와이프 도중의 임시 노출은 조회로 세지 않고, 사용자에게 실제 표시된 페이지로 판정한다. Compose 재구성, 같은 페이지로의 단순 포그라운드 복귀, 처리 중 중복 탭은 새 이벤트로 기록하지 않는다. 실제 실패 후 수락된 완료 상태 저장 재시도는 submit을 다시 기록한다.

기존 `destination_alarm_created` 이벤트는 홈에서 사용자가 별도로 알람을 만들 때 유지한다. 온보딩 완료만으로 이 이벤트를 기록하지 않는다. 중간 단계 통과는 다음 페이지 조회로 판정하므로 별도의 단계 완료 이벤트는 추가하지 않는다. 권한별 실패·버튼별 클릭·앱 종료 이벤트는 이번 범위에서 제외한다.

## 이전 버전에서 전환

v1은 `flow_name = first_alarm`, `flow_version = 1`인 첫 알람 생성 흐름이었다. Android는 시간 → 요일 → 목적지 → 반복 간격 → 알람음의 5단계, iOS는 알람음을 제외한 4단계였다. v2는 입력 없이 소개를 읽고 완료하는 흐름이므로 v1의 알람 저장 성공률과 v2의 소개 완료율을 같은 지표로 합치지 않는다.

- 기존 DataStore의 온보딩 완료 상태를 그대로 사용한다. 이미 온보딩을 마친 사용자는 업데이트해도 소개 페이지를 다시 보지 않는다.
- 시작·완료 이벤트의 영구 claim은 기존 Android SharedPreferences·iOS NSUserDefaults의 `first_alarm` 식별자를 유지한다. 이벤트 파라미터의 새 `flow_name`이나 앱 버전에 맞춰 저장 키를 변경하지 않는다.
- v1 시작만 기록한 채 업데이트한 사용자는 v2 페이지를 볼 수 있지만 begin을 다시 기록하지 않는다. v2 complete가 기록될 수 있으므로, v2 최초 시작 코호트에는 v2 begin이 있는 설치만 포함한다. 버전 전환 중 완료는 별도로 관찰한다.
- 기존 완료 상태나 Analytics claim을 초기화하는 마이그레이션을 수행하지 않는다.

## 연결 위치와 중복 방지

- `OnboardingRoute`에서 실제 표시된 페이지를 `OnboardingViewModel.onStepVisible()`에 전달한다. ViewModel의 마지막 표시 페이지로 재구성·Activity 재생성 중복을 막는다. 앱 프로세스 재시작 후에는 새 조회를 기록한다.
- 마지막 페이지의 완료 요청이 수락됐을 때 submit을 기록한다. 온보딩에서 `AlarmSetupCoordinator`나 알람 저장·권한 확인을 호출하지 않는다.
- `AppBootstrapViewModel`은 `markOnboardingCompleted()` 성공 뒤 완료 이벤트를 기록한다. 온보딩 화면이 홈으로 전환되어 제거돼도 완료 기록을 화면 수명주기에 의존하지 않는다.
- `DefaultProductAnalyticsRecorder`에서 공통 이벤트와 파라미터를 만든다. Android Firebase 어댑터와 iOS Swift Firebase 어댑터에 기존 경로로 전달한다.
- 최초 시작·완료 claim은 앱 버전이나 프로세스 수명에 따라 초기화하지 않는다.
- 기존 Analytics와 동일하게 로컬 claim 후 SDK에 전달하는 방식이다. 앱 강제 종료나 SDK 호출 오류 사이의 유실 가능성이 있으며 서버 수신의 exactly-once를 보장하지 않는다. Analytics 오류 때문에 온보딩 완료 상태 저장을 실패시키지는 않는다.

## 지표와 관찰 기간

초기 관찰 기간은 최초 시작 이벤트부터 24시간이다. 시작이 관측되고 24시간이 지난 설치만 확정 지표에 포함한다. 앱 재실행으로 관찰 기간을 초기화하지 않는다.

| 지표 | 분모 | 분자 |
| --- | --- | --- |
| 페이지별 미진행률 | 해당 페이지에 순서대로 도달한 고유 설치 | 24시간 내 다음 구간에 도달하지 못한 설치 |
| 전체 완료율 | 시작한 고유 설치 | 24시간 내 완료한 설치 |
| 완료 요청 후 미완료율 | 완료 요청한 고유 설치 | 24시간 내 완료되지 않은 설치 |

마지막 소개 페이지의 다음 구간은 submit이다. 반복 조회와 재시도는 구간별 설치당 1회로 집계한다. 24시간 이후 완료는 지연 완료로 별도 확인한다. 앱 종료 후 24시간 내 복귀·완료한 설치는 전체 이탈로 세지 않는다. 해당 버전의 시작 이벤트가 없는 기존 사용자는 최초 시작 코호트에서 제외한다. 계정이 아닌 설치 단위이므로 재설치·데이터 초기화로 사용자 단위가 달라질 수 있다. 이벤트 미관측을 사용자의 의도적 포기로 단정하지 않는다.

## Firebase / GA4에서 별도로 할 작업

앱 코드 변경만으로 운영 콘솔의 설정이 생성되지는 않는다.

1. 이벤트 범위 맞춤 측정기준으로 `flow_name`, `flow_version`, `step_name`, `step_index`, `step_count`를 등록한다. 모두 분류/필터 용도로 사용하며 합계 지표로 해석하지 않는다.
2. Android·iOS별 퍼널을 만들고 `flow_name = service_introduction`, `flow_version = 2`로 필터링한다. 기존 v1 퍼널은 이전 흐름 분석용으로 보존한다.
3. 정확한 최초 시작 기준 24시간 코호트 분석은 BigQuery 등에서 별도로 구성한다. 단순 단계 간 제한 시간과 혼동하지 않는다.
4. 디버그 기기에서 Firebase DebugView로 아래 시나리오를 확인하고 운영 분석에서 테스트 트래픽을 제외한다.

## 검증 시나리오

- 정상 Android·iOS 흐름: begin → introduction → destination → interval → departure → submit → complete.
- 재구성·단순 앱 복귀에서는 같은 페이지 조회가 늘어나지 않는다.
- 스와이프·다음 버튼·이전 페이지 이동으로 실제 표시된 페이지 조회가 기록된다. 옆 페이지 사전 구성은 조회가 아니다.
- 앱 재실행에서 begin은 늘어나지 않고 introduction 조회만 추가된다.
- 마지막 페이지에서 시작하기를 누르기 전에는 submit이 발생하지 않는다.
- 완료 상태 저장 중 중복 탭에서는 submit이 늘어나지 않는다. 실패 후 재시도에는 submit이 추가된다.
- 완료 상태 저장 실패 시 complete가 발생하지 않고, 성공한 재시도에서만 complete가 기록된다.
- 온보딩 완료 시 알람 생성·예약·권한 요청이나 `destination_alarm_created`가 발생하지 않는다.
- begin·complete는 기록기/저장소 인스턴스를 다시 만들어도 중복되지 않는다.
- v1 완료 사용자가 업데이트하면 홈으로 진입하고 새 begin·complete를 기록하지 않는다. v1 begin만 기록한 사용자는 v2 begin을 다시 기록하지 않는다.
- 주소·좌표·이름·검색어·시각·알람음 URI·원시 DB 키와 자유 텍스트는 파라미터에 포함하지 않는다.
