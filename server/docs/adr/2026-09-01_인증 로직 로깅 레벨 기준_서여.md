# 인증 로직 로깅 레벨 기준

- 작성일: 2026-09-01
- 작성자: 서여
- 결정 대상: 링아웃 서버의 비지니스 로직에서 사용하는 로깅 레벨 기준

## 배경

회원가입, 로그인, 토큰 발급은 인증 흐름의 핵심 경로다. 이 구간에서 장애가 발생하면 사용자는 서비스에 진입하지 못하고, 서버 담당자는 실패 원인이 클라이언트 요청 문제인지, 외부 소셜 인증 문제인지, 서버 내부
문제인지 빠르게 구분해야 한다.

기존에는 인증 흐름의 주요 분기와 실패 원인을 로그로 확인하기 어려웠다. 단순히 "로그인 시작", "로그인 완료"처럼 메서드 실행 여부만 남기면 운영 중 실패 원인을 판단하기 어렵고, 반대로 토큰, 이메일, 소셜
providerId 같은 값을 그대로 남기면 민감 정보 노출 위험이 생긴다.

따라서 인증 로직에 로그를 추가하되, 로그 레벨과 기록 범위를 먼저 정해야 한다.

## 결정 요인

- 운영자가 로그만 보고 인증 실패 원인을 구분할 수 있어야 한다.
- 토큰 원문, 이메일, 소셜 providerId 등 민감 정보와 개인 식별 가능 정보는 로그에 남기지 않아야 한다.
- 로그 레벨은 코드의 심각도 표현이 아니라 운영 대응 우선순위와 알림 정책의 입력값이어야 한다.
- 사용자 또는 클라이언트 입력으로 발생한 예상 가능한 실패와 서버가 정상 책임을 수행하지 못한 실패를 구분해야 한다.
- 정상 흐름 로그는 장애 분석에 필요한 상태 전이를 설명해야 하며, 단순 시작/종료 로그는 지양해야 한다.

## 고려한 대안

### 대안 1: 모든 인증 실패를 error로 기록

## 장점

- 인증 실패가 눈에 잘 띄어 초기 장애 인지가 쉽다.
- 실패 로그를 한 레벨에서만 찾으면 되어 검색 조건이 단순하다.

## 단점

- 만료된 토큰, 빈 토큰, 잘못된 provider 같은 예상 가능한 요청 실패까지 서버 장애처럼 보인다.
- error 로그가 많아지면 실제 서버 장애 신호가 묻힌다.
- 운영 알림이 과도하게 발생할 수 있다.

### 대안 2: 모든 인증 실패를 warn으로 기록

## 장점

- 사용자 입력 오류와 인증 실패를 서버 장애로 과대 해석하지 않는다.
- 운영 알림 피로도가 낮아진다.
- 실패 원인을 reason 필드로 구분하면 집계와 분석이 가능하다.

## 단점

- 서버 설정 누락, 코드 버그, 토큰 발급 실패 같은 실제 장애도 warn에 섞이면 즉시 대응이 늦어질 수 있다.
- error 로그 기준 모니터링에서 인증 내부 장애를 놓칠 수 있다.

### 대안 3: 실패 성격에 따라 info, warn, error를 구분한다

## 장점

- 정상 상태 전이, 예상 가능한 실패, 서버 책임 실패를 로그 레벨로 구분할 수 있다.
- 운영 알림 기준을 error 중심으로 잡을 수 있고, warn은 추세 분석 대상으로 볼 수 있다.
- 장애 분석 시 실패 지점과 대응 우선순위를 빠르게 판단할 수 있다.

## 단점

- 로그를 추가할 때마다 실패 원인이 어느 레벨에 속하는지 판단해야 한다.
- 팀 내 기준이 공유되지 않으면 같은 종류의 실패가 다른 레벨로 남을 수 있다.

## 결정

인증 로직의 로깅 레벨은 실패 성격에 따라 구분한다.

`info`는 정상적인 인증 흐름에서 운영자가 상태 전이를 확인할 필요가 있는 경우에 사용한다. 예를 들어 소셜 로그인 요청 수신, 소셜 인증 성공, 기존 회원 로그인 성공, 신규 회원 가입 필요, 토큰 발급 성공이
해당한다.

`warn`은 개발자가 예상한 비정상 상황이지만 서버 전체 장애로 보기는 어려운 경우에 사용한다. 예를 들어 빈 소셜 액세스 토큰, 지원하지 않는 provider 요청, 소셜 인증 실패, 유효하지 않은
signupToken 또는 refreshToken이 해당한다.

`error`는 서버가 기대한 책임을 수행하지 못했고 운영자가 확인해야 하는 경우에 사용한다. 예를 들어 enum에 존재하는 provider의 SocialLoginClient가 등록되지 않은 경우, JWT 생성
실패, DB 조회 또는 저장 중 예외, 예상하지 못한 RuntimeException이 해당한다.

로그 메시지는 고정된 `reason` 값을 포함해 실패 원인을 구분한다. 단, accessToken, refreshToken, signupToken, socialAccessToken, 이메일, 소셜
providerId는 로그에 남기지 않는다. 사용자를 식별해야 하는 정상 로그인 이후 흐름에서는 내부 식별자인 userId를 사용한다.

## 긍정적 결과

- 인증 실패가 클라이언트 요청 문제인지, 외부 인증 문제인지, 서버 내부 문제인지 구분된다.
- 민감 정보와 개인 식별 가능 정보의 로그 노출 위험이 줄어든다.
- error 로그를 운영자가 즉시 확인해야 하는 서버 책임 실패에 집중할 수 있다.
- warn 로그를 통해 인증 실패의 추세와 반복 원인을 분석할 수 있다.
- 정상 로그인, 신규 회원 가입 필요, 토큰 발급 성공 같은 상태 전이를 운영 로그로 확인할 수 있다.

## 부정적 결과와 트레이드오프

- 로그를 추가할 때마다 레벨 판단 비용이 생긴다.
- warn 로그가 많아질 수 있으므로 reason별 집계 기준이 필요해질 수 있다.
- 외부 소셜 인증 실패가 대량으로 발생해도 개별 로그 레벨은 warn이므로, 장애 감지는 warn 발생량 기반 모니터링이 별도로 필요하다.
