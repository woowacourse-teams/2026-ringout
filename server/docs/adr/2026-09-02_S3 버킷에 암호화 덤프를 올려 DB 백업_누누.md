# **공용 S3 버킷에 클라이언트 암호화 덤프를 올려 DB를 백업**

- 작성일: 2026-09-02
- 작성자: 누누
- 결정 대상: 링아웃 운영 DB의 백업 저장 위치와 보호 방식, 그리고 목표 복구 지표

## 배경

Flyway 도입 이전 ddl-auto: update로 스키마를 관리하던 기간에 드리프트를 겪었다. 컬럼 삭제나 타입 변경이 반영되지 않아 실제 스키마와 엔티티 정의가 어긋났다. 이때 되돌릴 수단이 없었다. Flyway로 스키마 변경 이력은 관리되기 시작했지만, 마이그레이션이 데이터를 잘못 건드렸을 때 복구할 방법은 여전히 없다.

우테코가 제공하는 S3 저장소는 공용으로 8기 전체가 공유하며, 팀별 폴더로만 구분된다. 가른 팀의 산출물이 보이는 구조다.

링아웃 DB에는 소셜 로그인 식별자와 이메일이 들어 있다. 개인정보처리방침에 동의를 받고 수집한 데이터를 제3자가 열람 가능한 위치에 두는 것은 그 방침과 어긋날 소지가 있다. 저장 위치를 고르는 문제와 내용을 보호하는 문제를 함께 풀어야 했다.

## 결정 요인

- 인스턴스나 볼륨이 손실되어도 백업이 함께 사라지지 않아야 한다.
- 같은 버킷에 접근 가능한 다른 팀이 덤프 내용을 읽을 수 없어야 한다.
- 사람이 수동으로 매일 챙기지 않아도 동작해야 한다.(백업)
- 복구 목표는 추정이 아니라 측정된 값으로 정한다.
- 백업이 조용히 실패했을 때 알아챌 수단이 필요하다.

## 고려한 대안

### 대안 1: DB EC2 로컬 디스크 보관

/home/ubuntu/mysql/backups/ 에 cron으로 덤프를 쌓고 일정 기간만 남긴다.

## 장점

- 구성이 가장 단순하고 즉시 적용할 수 있다.
- 데이터가 인스턴스 밖으로 나가지 않아 노출 경로가 없다.
- 외부 서비스 권한에 의존하지 않는다.

## 단점

- 인스턴스나 EBS 볼륨이 손실되면 백업도 함께 사라진다. 재해 복구 수단으로는 무효다.
- 오직 “마이그레이션 직전 되돌리기” 용도로만 유효하다.

### 대안 2: EBS 스냅샷

DB EC2의 볼륨을 통째로 스냅샷으로 뜬다.

## 장점

- 볼륨 단위라 복원이 가장 빠르고, 논리 덤프에서 발생할 수 있는 스키마 불일치 문제가 없다.
- AWS 관리 영역에 저장되므로 암호화를 별도로 신경 쓸 필요가 없다.
- 다른 팀에 노출되지 않는다.

## 단점

- ec2-project role에 스냅샷 권한이 있는지 확인되지 않았고, 우테코 문서에도 언급이 없었다.
- 특정 테이블만 골라 복원하는 것이 어렵다.

### 대안 3: 공용 S3 버킷 + 서버사이드 암호화

공용 S3에 올리고 기본 S3 암호화에 맡긴다.

## 장점

- 별도 구현 없이 저장 시 암호화가 적용된다.
- 패스프레이즈를 관리할 필요가 없다.

## 단점

- SSE-S3는 AWS가 키를 보유하므로, 객체 읽기 권한만 있으면 복호화된 평문이 내려온다. 물리 디스크 탈취는 막지만 공용 버킷의 다른 팀에 대해서는 방어 효과가 없다.
- 이 시나리오에서는 보호하려는 대상(8기 타팀)과 방어 수단이 어긋난다.

### 대안 4: 공용 S3 버킷 + 클라이언트 암호화(채택)

덤프를 EC2에서 암호화한 뒤 S3에 올린다. 파일이 인스턴스를 떠나는 시점에 이미 암호문이다.

## 장점

- 인스턴스 손실과 타 팀 열람을 동시에 막는다.
- mysqldump, gzip, openssl이 파이프로 이어져 평문이 디스크에 닿지 않는다.
- 논리 덤프라 전체 복원과 특정 테이블 복원을 모두 할 수 있다.

## 단점

- 패스프레이즈를 관리해야 하고, 분실하면 백업 전체를 잃는다.
- 볼륨 단위 복원보다 시간이 많이 들고, 데이터가 커질수록 선형으로 증가한다.

## 결정

`techcourse-project-2026` 버킷의 `ringout/backups/mysql/YYYY/MM/DD/` 경로에 암호화된 덤프를 올린다. 파일명은 `ringout-20260902T080738Z.sql.gz.enc` 형태의 압축형을 쓴다. 시간순 정렬이 되어 최신 백업을 찾는 데 별도 로직이 필요 없다.

암호화는 클라이언트 측에서 수행한다. `openssl enc -aes-256-cbc -pbkdf2 -iter 200000 -salt`를 쓰고, 패스프레이즈는 `/home/ubuntu/mysql/.env`에서 환경변수로 전달한다. mysqldump는 `--single-transaction`으로 실행해 운영 중 테이블 락 없이 일관된 스냅샷을 얻는다.

DB EC2의 cron으로 매일 새벽3시에 실행한다. 스크립트는 `set -euo pipefail`로 파이프 중간 실패를 잡고, 결과 파일이 비어 있으면 업로드하지 않고 종료한다. 이 검사가 없으면 mysqldump가 실패해도 빈 파일이 그대로 올라가 복원 시점에야 문제를 알게된다. 실행 결과는 `backup.log`에 누적하며, 이것이 백업 실패를 감지하는 수단이된다.

복원은 자동화하지 않는다. 잘못 발동한 자동 복원은 멀쩡한 데이터를 과거 시점으로 덮어쓴다. 백업 실패는 데이터를 잃을 뿐이지만 잘못된 자동 복원은 데이터를 적극적으로 파괴하므로, 실행 여부는 사람이 판단한다.

RPO: 24hours

일 1회 백업이므로 최악의 경우 직전 24시간의 데이터가 유실된다. 알람 앱 특성상 이 구간의 손실은 사용자가 재현 가능한 성격이며, 결제나 금전 거래처럼 되돌릴 수 없는 데이터를 다루지 않는다. 더 짧게 RPO를 잡는 것은 binlog 기반 시점 복구를 요구하는데, 이는 별도 저장소와 운영 부담을 수반하므로 현 단계에서는 과도하다고 판단했다.

RTO: 약 25초

2026-09-02 측정값이다. 덤프 크기 4KB 기준.

| 구간 | 내용 | 측정값 | 방법 |
| --- | --- | --- | --- |
| A | S3 다운로드 | 약 1.5초 | 3회 평균(1.710 / 1.361 / 1.449) |
| B | 복호화 + 압축 해제 + 임포트 | 약 0.8초 | 전체 2.333초에서 A 구간 제외 |
| C | 앱 컨테이너 재기동 | 약 22초 | 기동 로그 19.003초 + 컨테이너 제어 오버헤드 추정 |
| 합계 |  | 약 25초 |  |

C 구간은 운영 컨테이너의 기동 로그에서 읽었다. 실제로 정지 및 기동하여 측정하면 그동안 서비스가 중단되므로, 이미 기록된 부팅 시간을 근거로 삼고 컨테이너 제어 오버헤드만 추정치로 더했다.

전체 소요의 대부분을 앱 기동이 차지한다. 복원 자체는 2.3초이고 애플리케이션 기동은 19초로, 8배 이상 차이가 난다. 현재 데이터 규모에서 RTO의 병목은 백업 설계가 아니라 스프링 부트 기동 시간이다. 백업 방식을 더 빠른 것으로 바꾸어도 전체 복구 시간은 거의 줄지 않는다.

이 수치에는 장애를 인지하고 어느 시점으로 복원할지 판단하는 시간이 포함되어 있지 않다. 복원을 수동으로 두기로 했으므로 실제 RTO는 사람의 대응 속도가 지배한다.

## 긍정적 결과

- 인스턴스와 볼륨이 모두 손실되어도 데이터를 복구할 수 있다.
- 공용 버킷을 쓰면서도 다른 팀이 개인정보가 담긴 덤프를 읽을 수 없다.
- 마이그레이션 전후로 되돌릴 지점이 생겨, 스키마 변경에 따르는 부담이 준다.
- RPO와 RTO가 측정값으로 문서화되어, 다음에 개선할 지점을 근거를 갖고 고를 수 있다.
- 복원 소요의 병목이 백업이 아니라 앱 기동이라는 사실이 확인되어, 당분간 백업

## 부정적 결과와 트레이드오프

- 패스프레이즈 분실은 백업 전체의 손실을 뜻한다. 팀 공유 저장소에 보관하고 있으나, 이 보관 자체가 새로운 단일 실패 지점이다.
- 오래된 백업을 정리하는 로직이 없어 파일이 무한히 누적된다. 현재 4KB 수준이라 당장 문제되지 않지만, 공용 버킷이므로 비용이 우테코 계정에 잡힌다.
- 백업 실패를 알리는 수단이 로그 파일뿐이다. 사람이 주기적으로 확인하지 않으면 며칠간 실패한 채로 방치될 수 있다.
- 측정값이 4KB 기준이라 A, B 구간의 의미가 작다. 데이터가 늘면 두 구간은 선형으로 증가하므로, 덤프가 수십 MB에 도달하는 시점에 재측정이 필요하다.
- DB EC2는 여전히 단일 인스턴스다. 백업은 데이터 손실을 막을 뿐 가용성을 높이지 않으며, 인스턴스가 죽으면 새 EC2를 띄우는 시간이 통째로 복구 시간에 더해진다.
