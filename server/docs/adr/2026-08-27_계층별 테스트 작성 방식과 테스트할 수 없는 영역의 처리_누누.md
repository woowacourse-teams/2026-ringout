# 계층별 슬라이스 테스트로 인증, DB, 외부 의존 격리

- 작성일: 2026-08-27
- 작성자: 누누
- 결정 대상: 링아웃 서버의 계층별 테스트 작성 방식과 테스트할 수 없는 영역의 처리

## 배경

JPA를 사용하지 않는 레벨2 미션에서는 서비스 계층을 테스트할 때 모킹, 컨트롤러 통합 테스트, Fake 객체 세 가지를 비교한 뒤 Fake를 선택했다. 모킹은 스텁과 검증이 구현 세부에 결합되어 리팩터링 시 테스트가 깨지고, 통합 테스트는 검증 범위가 너무 넓다는 이유였다. 컨트롤러처럼 단위 테스트가 어려운 부분은 통합 테스트 하나로 갈음할 수 있었다.

링아웃에서는 이 전략이 그대로 통하지 않았다. 조건이 달라졌기 때문이다.

- 소셜 로그인, 운영 환경의 MySQL, 인프라 환경
- JPA 사용
- 대부분의 API가 인증(AuthenticationPrincipal) 필요
- 실패 시 운영 장애

## 결정 요인

- 테스트 실행이 외부 시스템(소셜 로그인 등)에 실제 요청을 보내지 않아야 한다.
- 로컬과 CI 환경 어디서든 도커만 있으면 같은 결과가 나와야 한다.
- 쿼리와 스키마 검증은 MySQL에서 수행해야 한다.
- 전체 테스트 빌드 속도가 유지되어야 한다. 테스트 클래스마다 컨텍스트를 새로 띄우지 않는다.
- 인증이 컨트롤러 테스트 작성을 막지 않아야 한다.
- 작은 단위의 테스트를 쌓아 큰 단위의 동작을 설명할 수 있어야 한다. 통합 테스트 하나로 갈음하는 방식은 실패 시 원인 계층을 특정하기 어렵다.

## 고려한 대안

### 대안 1: Port 인터페이스 + Fake 객체

서비스와 JPA 사이에 실제 사용하는 메서드만 가진 좁은 인터페이스를 두고, 테스트에서는 인메모리 Fake를 주입한다.

## 장점

- 스텁과 검증이 구현 세부에 결합되지 않아 리팩터링에 강하다.
- 스프링 컨텍스트 없이 실행되어 가장 빠르다.

## 단점

- 서비스가 JpaRepository를 직접 의존하는 현재 구조에서는 불가능하고, 프로덕션에 구현체가 하나뿐인 인터페이스를 도메인마다 추가해야 한다.
- 기술 스택 선정 문서의 "단순 도메인은 레이어드, 복잡한 도메인만 port-adapter 부분 적용" 방침과 충돌한다.
  테스트 편의가 아키텍처 방침을 앞지르게 된다.

### 대안 2: @SpringBootTest 통합 테스트 중심

전체 컨텍스트와 실제 DB로 큰 단위를 검증한다.

## 장점

- 빈 조립과 트랜잭션 경계까지 실제로 검증된다.
- 계층별 테스트를 따로 유지하지 않아도 된다.

## 단점

- 모든 API가 인증을 요구하므로 테스트마다 토큰 준비가 필요하다.
- 전체 컨텍스트 로딩과 DB 준비로 느리고, @MockitoBean 조합이 바뀔 때마다 컨텍스트가 재생성되어 빌드 시간이 늘어난다.
- 실패했을 때 도메인, 서비스, 매핑, 쿼리 중 어디가 원인인지 특정하기가 어렵다.
- 외부 시스템을 결국 격리해야 하므로, 진정한 통합테스트가 아닐 수 있다.

### 대안 3: 계층별 슬라이스 + 애플리케이션의 외부  영역 격리(채택)

계층마다 검증 대상과 대체 수단을 다르게 정하고, 각 계층의 테스트가 자기 계층만 책임진다.

## 장점

- 인증, DB, 외부 의존이라는 세 가지 장애물을 계층별로 하나씩만 처리하면 된다.
- 리포지토리만 MySQL을 쓰므로 느린 테스트의 범위가 한정된다.
- 실패한 테스트의 계층이 곧 원인이 된다.
- 현재 구조(서비스의 JpaRepository 직접 의존)를 바꾸지 않는다.

## 단점

- 서비스 테스트가 Mockito 스텁에 의존해 구현 세부와 결합된다.
- 계층 사이의 조립은 어떤 슬라이스도 검증하지 않는다.

## 결정

서비스 계층은 Mockito를 사용한다. 구현 결합의 비용은 감수하되, 스텁은 가능한 최소한으로 하고 verify는 상태 검증으로 대체할 수 없는 경우에만 사용한다.

리포지토리는 운영과 같은 방식으로 검증한다. Testcontainers로 DB 컨테이너를 띄우되, 테스트 클래스마다 새로 띄우지 않고 컨테이너 하나를 재사용하도록 구성한다. 재사용에 따른 테스트 간 데이터 격리는 @DataJpaTest의 트랜잭션 롤백에 맡기고, 롤백으로 부족한 경우에만 정리하는 코드를 추가한다.

컨트롤러는 spring-security-test로 인증 필터를 태우지 않고 검증한다. spring-security-test의 @WithSecurityContext 기반 애노테이션으로 인증 객체를 컨텍스트에 심어 주입한다. 인증 필터와 토큰 파싱은 컨트롤러 슬라이스의 검증 대상이 아니다. 요청 파라미터 바인딩, 상태 코드, 공통 응답 형식과 에러 코드가 검증 대상이다.

테스트할 수 없는 영역(블랙박스)은 격리하고, 전이를 막는다. 테스트 불가능 영역의 문제는 그 영역 자체가 아니라 이를 의존하는 코드까지 테스트 불가능해지는 전이다. 경계에서 끊고 그 너머는 격리한다.

- 컨트롤러의 인증 토큰 검증
    - 테스트하지 않는다. 경계 인터페이스 뒤로 격리해 이를 의존하는 서비스는 테스트 가능하게 유지한다.
- 운영 환경에서 발생하는 트래픽과 장애
    - 사전 테스트로 막지 않는다. 운영 로그로 탐지하고, 원인을 로컬에서 재현한 뒤 테스트로 고정한다.

## 긍정적 결과

- 인증 기능과 무관하게 각 도메인 담당자가 테스트를 작성할 수 있다.
- 스키마와 쿼리 문제를 운영과 같은 엔진에서 배포 전에 잡는다.
- 실패한 테스트의 위치가 원인 계층을 가리켜 디버깅 범위가 줄어든다.
- 느린 테스트의 범위가 레포지토리 슬라이스로 한정되어 빌드 속도를 통제할 수 있다.
- 테스트 불가능 영역이 격리되어, 테스트 불가능 영역이 전이되지 않는다.

## 부정적 결과와 트레이드오프

- 서비스 테스트가 스텁 정의에 결합되어 리팩터링 테스트 수정 비용이 든다.
- 서비스-리포지토리 조립, 트랜잭션 경계, 빈 주입 오류는 어떤 슬라이스도 잡지 못한다. 통합 테스트 도입을 검토해야 할 부분이다.
- 재사용 컨테이너는 테스트 간 데이터 격리 책임을 테스트 코드로 가져온다. 롤백이 적용되지 않는 테스트가 생기면 격리 실패가 다른 테스트의 간헐적 실패로 나타날 수 있다.
- 컨테이너 재사용 설정은 로컬 도커 환경에 의존한다. 도커가 없는 환경에서는 레포지토리 테스트가 실행되지 않는다.
